# v3 架构与可靠性设计

本版本在用户现有仓库基线 `94c3db3` 上增量改造。应用仍采用本机 Python HTTP 服务、浏览器界面和 SQLite，不引入共享服务器或远程数据库。原有平台读取、登录助手、存储及 Agent Harness 能力被复用并调整，贡献归属见版本说明。

## 主要流程

```text
用户关键词、目标、排除词
  → 纯规划模块生成可编辑草案
  → 用户确认计划与预算
  → 平台读取适配器采集
  → 正文读取、主题相关性、独立评论分析
  → 需求分类、证据校验、逐条 QA
  → 人工审核
  → 结果导出 / 单条触达预览
  → 用户再次确认触达
  → 账号、目标复验 → 提交 → 回执核验
```

规划阶段不构造平台采集器。模型不可用会明确返回手动草案，不假装已经完成 AI 规划。执行保存确认后的计划及 hash，便于重跑、审计和比较。

## 状态和质量控制

人工审核依据包含来源证据和搜索意图的 hash。重复获取同一内容和意图可以复用已有审核；证据或搜索意图变化时，不继承原通过结论。任务是否执行成功与分类是否准确分开统计，不能以 API 返回成功率替代模型质量。

固定评测集按笔记分组划分调试集和冻结验收集，避免同一笔记泄漏到两侧。`autoPassed` 仅表示自动指标通过，不等于 `passed`。管理员必须逐条核验全部输出的引用与虚构信息，并通过 `/api/evals/review` 留下核验样本 ID、备注和确认记录；只有自动门槛与完整人工核验共同通过后，才可凭对应版本和 hash 的记录明确启用候选。反馈不会自动变成线上 Prompt。

### 智能体定制开发的证据约束

计划中的 `offeringId=agent_custom_development` 表示单项服务模式；`general` 表示通用关键词研究。聚焦模式下，只有 `intent_role=buyer`、`service_fit=custom_development`、`demand_origin=self`，并且两类本人证据均有效，才允许保留明确需求线索：

- `customization_evidence`：本人具体场景或定制开发需求的原文片段。
- `commissioning_evidence`：本人寻求外部开发、承接、委托或报价的原文片段。

两项均须为非空字符串数组，每一项都必须逐字出现在传给模型的候选 `content` 中。候选内容去除系统凭据，保留商机手机号、邮箱及来源编号。评论候选只能引用自己的评论，不能借用所在笔记、其他评论或模型改写文本。`demand_origin=third_party/unclear` 或缺少必要字段时不能按本人委托认定。服务商归为宣传，讨论归为信息，不匹配该服务的内容归为无关；证据不足保留待确认。降级依据另存 `intent_reason`，保留模型原始 `reason` 供复核。

这一约束对模型提供的结构和引用做校验，不用关键词正则代替语义判断。若模型把第三方需求误标为本人需求，且截取的引文确实存在，结构校验本身无法发现全部语义错误；人工来源核验仍是必要步骤。高分不能绕过约束，符合证据也不等于已成交或有公开预算。

本次服务规则是针对用户明确选择的服务范围新增的软件规则，由运行器独立附加，并记录 `servicePolicyVersion`。它不等于自动启用一个 Prompt 候选。实际执行当前启用的 Prompt；候选仍需评测和管理员明确启用，不设置旧版本兼容回退。执行记录区分基础 Prompt 版本和附加服务规则版本。

聚焦任务始终受两类本人证据约束，固定集评测也按实际样本的 `offeringId` 应用相同规则。原任务计划和产出不会因新默认值而覆盖；新设置通过新计划、新任务生效。

人工审核的依据包含服务范围。`general` 使用通用审核依据；相同原文切换到 `agent_custom_development` 时不继承通用模式的通过结论，需要重新审核。

| 触达状态 | 含义与后续动作 |
|---|---|
| `prepared` | 仅预览，尚未写入平台；令牌有效期 15 分钟 |
| `executing` | 数据库事务已领取该动作；重复调用不再执行 |
| `succeeded` | 存在与账号、目标、正文一致的验证证据 |
| `failed` | 已知未提交；修改问题后需重新预览和确认 |
| `unknown` | 可能已提交但回执不确定；先人工核验，不自动重发 |

令牌摘要绑定动作 ID、平台、目标、正文、账号和期限。执行前重新读取稳定账号 ID；不把昵称、Cookie 存在或“登录成功”布尔值当作身份。每次提交只点击一次，不用备用按钮或 Enter 猜测性重试。中断后遗留的执行记录恢复为未知，不能回退成待执行。

领取执行动作时先持久化 `confirmedAt` 和 `executionCount=1`，重复 HTTP 确认不改变这两个字段。次数表示本工作流执行尝试，是否实际提交另看 `submitted`。相同账号、平台、动作、目标与正文已有执行中或未知记录时，不能通过换动作 ID、线索 ID 或链接参数绕过重发限制；预先创建的第二份草案在执行时也会再次检查。

关注要求刷新后的目标关注状态；评论要求目标内容中出现新的本人评论；回复还要求绑定原评论；私信要求在明确目标会话中出现新的已发送回执。当前选择器未经真实平台完整验收，不满足唯一定位或回执条件即停止或记为未知。

## 数据边界

- 来源证据保存在 `task_entities`，按任务、类型、平台和实体 ID 隔离。当前结构通过完整建表语句初始化；已删除旧表迁移、回填与重命名。来源原文缺失时不借用其他任务数据；草稿、触达准备和反馈带任务 ID，服务端复验任务及所有者。
- SQLite、平台 profile、Cookie 和真实模型配置留在本机，均排除在源码包之外。
- 采集阶段只读；触达是独立、逐条确认的外部写操作。开发测试全部使用 mock/fixture。
- 模型请求会把任务必要的内容发给用户配置的接口，保留商机原文中的手机号、邮箱及来源编号。请求与日志过滤系统凭据及模型内部思考，不能改写用于匹配判断结果的来源编号。
- 外部页面和评论是待分析数据，不能作为授权执行指令。生成建议须回到来源核验。
- 服务面向本机单人管理员。若未来改为多人或共享部署，必须重新设计权限、数据隔离及并发浏览器账号管理。

## 当前证据边界

代码测试证明的是状态机和模拟条件下的行为。它不证明平台当前 DOM、实际账号权限、网络成功率或四周稳定性；这些必须按验收文档记录真实任务。Windows 启动与浏览器路径尚未实测。

## 当前实现的清理与回归约束

- 只保留 HarnessPipeline；旧 LeadPipeline、产品目录、评分报告模板、旧 API 和无调用的直接写平台入口已删除。
- 候选的初判另存 `preQaQualified`；只有本条 `qa_status=approved` 才计入 `qualifiedCount`。部分完成不会把待复核候选算作合格。
- 本地去重 ID 与平台 `source_comment_id` 分开。原始 ID 缺失时标记合成来源，不用于评论回复；相同文本的不同作者不合并。
- 批量审核标注使用一次查询；任务列表仅选取列表必要字段，不读取完整结果 JSON。
- 浏览器和服务启动失败均回收自有进程；先取得数据库独占锁再恢复中断任务，重复启动不会打断另一个实例。
- 配置保存比较提交快照，任务切换校验异步请求身份；HTML 转义不改写来源文本。
- 源码包校验文档相对链接，包含 README 引用的自进化说明，排除配置、业务数据和会话。
