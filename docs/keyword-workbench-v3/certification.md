# 中级申报材料与证据模板

建议方向为「AI Agent 工程化与可靠性」。本项目交付代码不等于申报人已满足中级资格；至少四周真实常态使用、本人关键判断和真实工作价值仍须由申报人实际完成并留证。

根据用户提供的考核材料，2026 年 10 月 30 日是首轮绩效累计节点，最终申报截止为 **2026 年 12 月 30 日 18:00（Asia/Shanghai）**。同一产品原则上不重复申报不同方向；每窗口驳回后只有一次再提交机会。所有代码、README 与补证统一维护在对应原 Git 仓库，补证不另建仓库。

## 六字段填写模板

| 表单字段 | 可采用的结构 | 必须补充的真实证据 |
|---|---|---|
| 成果名称 | 关键词研究与线索工作台：面向【本人岗位场景】的 Agent 工作流 | 真实项目名、原仓库、提交版本 |
| 应用场景 | 【谁】原先在【工作任务】中如何搜索、筛选、复核；问题和范围是什么 | 与本人岗位、公司、客户或内部工作的直接联系，原流程记录 |
| 目标用户 | 【本人/团队角色】在【频率】使用，结果用于【具体工作】 | 真实使用者、职责、使用记录与接收方反馈 |
| 工作流实现 | 关键词→计划预览→确认采集→分类与证据→人工审核→导出；触达独立二次确认 | 架构、关键取舍、权限、日志、重试边界、人工兜底、本人贡献 |
| 使用情况与效果 | 【实际起止日期】共【真实数量】任务；与【人工基线】比较【实际指标】 | 至少四周记录、至少 20 次任务、样本质量实测、失败处理和对比数据 |
| 质量与安全 | 来源核验、固定集自动指标与全量人工核验、候选人工启用、账号绑定、一次提交、未知结果人工核对 | 通过/失败标准、实测输出、逐条核验备注、异常案例、数据范围、隐私与密钥处理 |

可追加复盘：最初假设、真实误判或失败、采取的修正、复测结果、仍然存在的限制。尚未发生的内容写“待验证”，不填预计数字冒充实际效果。

## 对照中级门槛

- 初级明确要求至少四周持续使用，中级建立在初级之上。20 次任务、两个场景或 100 条测试样本都不能代替四周真实使用。
- 100 条人工标注样本与 20 次真实任务是本项目的验收安排，不应描述为截图原文中统一规定的数字。
- 稳定性须用真实运行数据说明；模型输出准确性须用人工标注和复核说明。不能以接口成功或脚本跑通代替质量证明。
- 无需绑定某款产品，但材料必须与真实岗位、公司、客户或内部场景相关。公开资料可以是输入，纯演示流程不足以构成真实使用证据。
- 同一产品优先选择一个申报方向，不将同一实现拆成多个名称重复申报。

## 贡献与来源

源仓库是用户自身已有仓库，基线为 `94c3db3`。基线及之前作者的署名、已有代码和历史贡献以原 Git 记录为准；本次新增能力不能覆盖或抹去这些贡献。

| 部分 | 贡献说明填写要求 |
|---|---|
| 原有平台读取、登录、存储、Harness | 说明复用来源与基线，不写成此次从零开发 |
| 本次关键词计划、复核、评测及触达工程改造 | 按实际提交说明新增/修改范围、AI 与协作者参与 |
| 申报人自己的工作 | 如实填写需求判断、设计决策、实现、实测、使用与复盘 |
| 外部协助 | 说明实际协助范围，不能将外部代做全部表述为本人独立完成 |

考核说明代码重合度达到或超过 80% 会被驳回。未知查重库、算法和范围下，**不能承诺低于 80%**；需要真实、可解释的差异和贡献记录，不为规避查重而改名、搬仓或伪造开发历史。

## 原仓库证据清单

建议在原仓库的受控证据目录维护经审核脱敏的材料；默认源码包不包含真实证据与数据库。禁止提交 Cookie、Token、密钥或完整账号 profile。

1. README、架构、本人关键决策及贡献说明。
2. 与真实岗位相关的任务背景、使用者及接收方说明。
3. 至少四周使用记录及至少 20 次任务表，每平台至少 5 次。
4. 冻结标注集说明、数据 hash、来源与标注方法、自动评测结果及全部输出的管理员核验记录；`autoPassed` 不等于最终 `passed`。
5. 正常与失败案例、处理前后对比、重试和人工兜底记录。
6. 真实版本、交付清单/hash、实测环境、验收意见与剩余风险。

提交前按这份清单进行一次完整自查，保留修订记录。补证继续在同一仓库中追加真实材料，不补造原本没有发生的使用、测试或确认。
